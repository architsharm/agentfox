# ADR 0002: Customer-authored rules, end-user responses and imports

**Status:** Accepted, 2026-10-08.

## Context

Customers asked for what Guardrails AI and NeMo Guardrails make easy: block their own words and
topics, keep an agent on its subjects, tell the end user something sensible when a request is
stopped, ask the model to fix an answer instead of refusing, tune how sensitive a check is, and
bring the guards they already wrote. Each could have been built as its own feature with its own
storage, screen and enforcement path. That is how a product ends up with five ways to decide and
no single place to see, test or audit a decision.

## Decision

1. **A customer's rule is data plus a policy rule.** The definition (words, patterns, a topic, a
   sequence of tools) is a `CustomRule` row read by one detector (`custom.lists`, plus the opt-in
   `custom.topics` model) and one check (`containment.custom_sequences`). The *decision* is a rule
   in a managed policy pack, `custom`, regenerated by `custom_store.sync_policy` alone. So custom
   rules go through the same engine, observe/enforce modes, simulation gate, versions, tuning
   screen and audit chain as shipped rules, and an operator's tuning survives an edit to the word
   list.
2. **What the end user sees is a property of the rule.** `Rule.message` (shown to the end user) is
   separate from `reason` (for operators and the audit log). `Rule.on_block: reask` makes the
   gateway proxy ask the model once more with the rule as the correction; guard endpoints return
   the instruction instead. Re-ask never applies to tool calls.
3. **Sensitivity is the detection threshold.** The dashboard's Low/Medium/High writes
   `when.detection.min_score`; there is no second sensitivity setting.
4. **Detectors are switched per workspace, not per deployment.** `detector_settings` overrides the
   deployment's `enabled_detectors`; a few are always on. Model-backed detectors (topics,
   grounding) are opt-in, load from local files only, and refuse to switch on when not installed.
5. **Importers only plan.** `capabilities/detection/importers/<tool>.py` reads another tool's
   configuration *without executing it* and returns an `ImportPlan` of custom rules, detectors and
   packs, with the rest skipped and named. Applying goes through `save_rules`, `set_enabled` and the
   library's `install`, so an import is audited and versioned like a hand-made change. A new tool is
   one module and one line in `IMPORTERS`.
6. **New semantic checks raise risks; packs decide.** Task drift (`judgment.task_alignment`),
   insecure code (`code.insecure`) and model-based grounding (`grounding.nli`) report risks or
   detections. The `agent-integrity` pack acts on them and ships watching.

## Consequences

- One screen tunes every rule; a custom rule appears in Policies like any other.
- `custom_store.save_rules` and `delete_rule`, and `detector_settings.set_enabled`, are privileged
  operations in `operator_log.PRIVILEGED`; the structural test fails if one stops recording.
- A bulk change (an import) is one version of the `custom` pack, reviewed and rolled back as one.
- Adding a rule to an enforcing `custom` pack simulates first, as the `/mode` route requires.
- Output formatting validators (length, JSON shape, casing) are not imported; AgentFox governs
  what an agent says and does, not how its output is laid out.

## Alternatives considered

- **A separate custom-rules engine.** Faster to write, but a second place where decisions happen,
  without modes, simulation or versioning.
- **Running Guardrails AI guards as-is.** Possible through `rails.guardrails_ai` and the Hub
  detectors, and still supported; but the customer would keep two configurations, and their
  validators would stay outside our tuning and precision data.
- **Executing imported Python to read it.** Exact, and unacceptable: the input is customer code.
